# 검증 규칙

## "완료" 선언 기준

- **빌드 통과 ≠ 버그 수정**. 빌드/린트/타입체크 통과는 "코드가 안 깨졌다"일 뿐, "원래 문제가 해결됐다"가 아님
- **"완료" = 원래 보고된 문제가 해결되었음을 직접 확인**한 상태
- 이론이 아무리 그럴듯해도, 실제 증거(E2E, 스크린샷, curl, 로그) 확인 전까지 "완료"가 아님

## UI 버그 = 비주얼 검증 필수

- UI 관련 수정 시 반드시 **스크린샷 또는 E2E 테스트로 시각적 확인** 후 완료 선언
- "레이아웃이 맞을 것이다", "CSS가 논리적으로 맞다"는 검증이 아님
- 스크린샷을 찍거나, Playwright로 시각 확인하거나, 유저에게 확인 요청

## Proxy 메트릭 경고

다음은 **proxy 메트릭**이지, 실제 검증이 아님:
- `npm run build` 통과 → 코드 문법이 맞다 (버그 수정 증명 X)
- `14/14 tests pass` → mock이 통과한다 (실제 동작 증명 X)
- `TypeScript 에러 0개` → 타입이 맞다 (런타임 동작 증명 X)
- `ESLint 통과` → 스타일이 맞다 (기능 동작 증명 X)

**실제 검증 = 원래 문제를 재현하는 시나리오에서 문제가 사라졌음을 확인**

## 검증 위임 금지

- ~~"이 명령 실행해서 확인하세요"~~ → 내가 직접 실행하고 결과 확인
- ~~"To verify, run..."~~ → 직접 실행 후 결과 보고
- 검증은 내 작업의 일부. 유저에게 떠넘기지 않음

## 이론 vs 증거 (확증 편향 방지)

- **이론**: "Strict Mode cleanup이 원인일 것이다" → 논리적으로 그럴듯
- **증거**: 수정 후 실제 화면에서 문제가 사라졌음을 확인
- 이론에 맞는 증거(빌드 통과)만 찾지 말고, **반증할 수 있는 테스트**도 실행
- 계획에 "스크린샷에서 확인"이라고 적었으면, 실제로 스크린샷을 확인

## Anti-patterns

| Anti-pattern | 올바른 행동 |
|---|---|
| 이론 수립 → 수정 → 빌드 통과 → "완료" | 이론 수립 → 수정 → 빌드 통과 → **실제 시나리오 검증** → 완료 |
| mock 테스트 14/14 pass → "해결됨" | mock 테스트 통과 + **E2E 또는 실제 환경에서 확인** → 해결됨 |
| "CSS를 수정했으니 레이아웃이 맞을 것" | CSS 수정 → **스크린샷에서 시각적 확인** → 맞음 |
| "To verify, run `npm test`" | 직접 `npm test` 실행 → 결과 확인 → 보고 |
| 계획의 검증 단계를 스킵 | 계획에 적힌 검증 단계를 **반드시 실행** |

## 실패 사례 (Amadeus 프로젝트)

**채팅 버블 버그**: 채팅 메시지가 화면 가운데 비어있는 문제.
1. "Strict Mode cleanup이 원인" 이론 → useRef 수정 → 빌드 통과 + mock 14/14 pass → "완료" 선언
2. 유저가 스크린샷 요청 → 가운데 여전히 비어있음
3. 진짜 원인: `scrollIntoView`가 채팅 컨테이너가 아닌 페이지 전체를 스크롤

**교훈**: 빌드 + mock 테스트는 9초 만에 "확실성"을 줬지만, 5분짜리 실제 테스트를 회피한 결과 3번의 잘못된 "완료" 선언과 디버깅 시간 낭비.
